# CARE-OS

CARE-OS is a role-based healthcare operations application with clinical records, prescriptions, pharmacy processing, patient status visibility, and CareAI decision-support predictions.

## Features

- JWT authentication with admin, doctor, pharmacy, patient, and receptionist roles.
- Role-scoped routing in the UI and resource-ownership checks in the API.
- Login throttling, security headers, and an audit trail of health-record access.
- Patient registration and management.
- New patient accounts generated by the backend (`PAT000001@CareOS`) with a random temporary password that must be rotated at first sign-in; login IDs are based on stable Patient IDs, never names.
- Doctor, appointment, and medical-record workflows.
- Doctor-scoped disease choices and an expanded medicine catalog for clinical workflows.
- Appointment advance-payment flow requiring a simulated 25% payment before confirmation, with UPI,
  UPI ID, credit-card, and debit-card methods. UPI displays the repository QR asset `UPI.svg`.
- Payment validation formats card numbers as four groups of four digits, requires a two-digit month
  and two-digit year, rejects expired cards, and limits CVV values to three digits.
- Scheduling observes weekly hours: Sundays are holidays, while Saturday appointments run from
  11:00 AM to 2:00 PM.
- Advance payments remain `Partially Paid` until the doctor successfully saves the consultation;
  that save settles the remaining balance and marks the appointment `Completed`.
- Receptionist-selected doctors are persisted as `assigned_doctor_id` and displayed in the patient's
  portal from the authenticated patient's record.
- Consultation recording is available only for scheduled appointments; cancelled or completed
  appointments cannot start a new consultation.
- Doctor dashboards mark patients as `Reviewed` once a medical record exists, preventing duplicate
  review actions for the same patient.
- Medicine catalog search from `Dataset/Medicine_Details.csv`.
- Doctor prescription creation using real clinical relationships.
- Automatic, idempotent pharmacy-order creation from prescriptions.
- Prescriptions use a catalogue medicine, one or more frequency selections (`Morning`, `Afternoon`,
  `Evening`), and a prescribed quantity (`5`, `10`, `15`, or `20`). Retired dosage, duration,
  instructions, and number-of-doses inputs are not required for new prescriptions; historical values
  remain readable when present.
- Patient pharmacy fulfillment supports a full or half quantity choice, followed by payment. The
  backend snapshots the fulfillment quantity without changing the doctor's prescription.
- Pharmacy order lifecycle:

```text
PENDING → PENDING_PAYMENT → READY_FOR_PICKUP → COLLECTED
```

Cash or on-counter payments remain pending until pharmacy staff confirm receipt. A successful digital
payment creates a one-time pickup token/QR payload; collection is authorized by an atomic backend
token check. Legacy pharmacy processing states (`ACCEPTED → PACKED → DISPENSED`) remain supported for
existing operational records.

- Patient-owned appointment, record, prescription, and pharmacy-order access.
- CareAI priority and wait-time predictions.
- MongoDB persistence and server-side authorization.

## Requirements

- Python 3.11+ recommended
- Node.js and npm
- MongoDB running locally
- MongoDB database: `care_os`

## Local MongoDB

Start MongoDB using the normal service command for your operating system. CARE-OS expects:

```text
mongodb://localhost:27017/
```

The database name is:

```text
care_os
```

On macOS with Homebrew:

```bash
brew services start mongodb-community@7.0
mongosh "mongodb://localhost:27017/care_os" --quiet --eval 'db.runCommand({ping:1})'
```

## Backend setup

```bash
cd Backend
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt        # API
pip install -r requirements-ai.txt     # CareAI models (omit and /ai returns 503)
pip install -r requirements-dev.txt    # test suite
```

Copy the safe environment template and configure local development values:

```bash
cp .env.example .env
```

At minimum, configure:

```env
ENVIRONMENT=development
HOST=127.0.0.1
PORT=8000
MONGODB_URI=mongodb://localhost:27017/
DATABASE_NAME=care_os
SECRET_KEY=replace-with-a-local-development-secret
CORS_ORIGINS=http://localhost:5173,http://127.0.0.1:5173
```

`CORS_ORIGINS` must list every exact origin the browser will use. `http://localhost:5173` and
`http://127.0.0.1:5173` are different origins; include both if the dev server may be reached
either way. Wildcards are rejected.

Outside development the application will not start unless `SECRET_KEY` is at least 32 characters
and `SEED_DEMO_USERS=false`.

Never commit `.env`, production secrets, database credentials, or API keys.

Start the API:

```bash
uvicorn main:app --reload
```

For a stable demo session, use:

```bash
uvicorn main:app --host 127.0.0.1 --port 8000
```

The backend is available at:

```text
http://localhost:8000
```

Health check:

```bash
curl http://localhost:8000/health
```

## Optional legacy demo clinical data

`ensure_demo_users()` creates the five logins but does not link them to clinical records. Without
the step below the doctor and patient portals load empty and no prescription can be written, because
`DoctorMeet@CareOS` has no `doctor_id` and `PatientMeet@CareOS` has no `patient_id`.

```bash
cd Backend
python -m scripts.seed_demo_clinical_data
```

This legacy command creates demo patients, appointments, and records for isolated local testing.
Normal startup removes retired `*DEMO` clinical records and creates only the hospital doctor
directory and linked development doctor accounts; patients and appointments must be created through
the app.

## Important API flows

### Login

```text
POST /api/v1/auth/login
GET  /api/v1/auth/me
POST /api/v1/auth/change-password
POST /api/v1/auth/register          administrators only
```

Account creation is an administrative action. There is no self-service registration, because the
role is caller-supplied. Repeated failed sign-ins are throttled per login ID and per client address
and return `429` with a `Retry-After` header.

### Clinical workflow

```text
POST /api/v1/patients
POST /api/v1/appointments
POST /api/v1/medical-records
POST /api/v1/prescriptions
```

The clinical relationship order is intentional:

```text
Patient → Appointment → Medical Record → Prescription → Pharmacy Order
```

Prescription creation requires the real `patient_id`, `doctor_id`, `appointment_id`,
and `medical_record_id`. CARE-OS does not fabricate clinical IDs or records when a
patient has not yet had a visit.

When a patient is registered, the backend persists the patient and creates a linked patient login.
The login ID is derived from the stable Patient ID (`PAT000001@CareOS`), never from the patient's
name; the password is a **randomly generated 14-character secret**, not derived from the name or
date of birth. It is returned once in the registration response, shown once on the success screen,
stored only as a bcrypt hash, and the account is flagged `must_change_password` so it has to be
rotated at first sign-in.

Creating a valid prescription automatically creates one pharmacy order.

### Pharmacy workflow

```text
GET   /api/v1/pharmacy-orders
GET   /api/v1/pharmacy-orders/{order_id}
PATCH /api/v1/pharmacy-orders/{order_id}/status
POST  /api/v1/pharmacy-orders/{order_id}/fulfillment
POST  /api/v1/pharmacy-orders/{order_id}/payment
POST  /api/v1/pharmacy-orders/{order_id}/confirm-cash
POST  /api/v1/pharmacy-orders/{order_id}/collect
```

Patients can choose fulfillment and pay only for their own orders. Pharmacy users confirm cash,
advance operational statuses, and collect orders using the secure pickup token. Patients can read only
their own orders; the prescription itself remains immutable through this fulfillment flow.

### Medicine search

```text
GET /api/v1/medicines/search?q=Augmentin&limit=20
```

### CareAI

```text
GET  /api/v1/ai/schema
POST /api/v1/ai/patient-priority
POST /api/v1/ai/wait-time
```

Both models one-hot encode their categorical inputs with `handle_unknown="ignore"`, so a value
outside the training vocabulary is silently dropped and the prediction stops depending on it.
`GET /ai/schema` returns the exact vocabulary read back out of the fitted encoders; the UI renders
those as dropdowns and the backend rejects anything outside them with `422` rather than returning a
hollow answer. `Severity` and `Severity_Score` are limited to the trained range 1-5.

`patient_id` is mandatory and ownership-checked: a patient may only ask about themselves, and a
doctor only about a patient they treat.

AI output is advisory decision support, not a diagnosis.

```bash

```

Live verification should be performed with MongoDB running. Important tests include authentication, role authorization, patient ownership, prescription creation, pharmacy transitions, AI access, and persistence after backend restart.

## Security rules

- Authentication is handled by the backend.
- Passwords are stored as hashes.
- JWT secrets come from environment configuration.
- Frontend role checks are for navigation only; backend authorization is authoritative.
- Patients cannot access other patients by changing IDs.
- Doctors cannot impersonate another doctor when creating prescriptions.
- Pharmacy users cannot modify clinical records or access CareAI.
- Do not expose model paths, model files, secrets, or database credentials.

## Current boundaries

Authentication, patient registration, appointments, consultations, prescriptions, pharmacy orders,
the admin overview, medical records, medicine search, notifications, and CareAI all read and write
backend data under server-side authorization.

A prescription still requires a real appointment and medical record, in that order. The
Appointments screen creates both.

Remaining mock content is limited to presentation-only copy on the patient and pharmacy dashboards
(care-team contacts, visit-assistance options, counter alerts, and appointment time-slot
availability). These are labelled in `Frontend/src/data/mockData.js` and are not used by any
clinical decision or write path.
